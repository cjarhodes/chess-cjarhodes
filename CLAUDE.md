# chess-cjarhodes

Static single-page chess training app served at https://chess.cjarhodes.com.

## Stack
- Static `index.html` + `styles.css` + `app.js` (no build step or package manager); opening content data (move lists, explanations, key ideas, variations) lives in `openings.js`, loaded before `app.js`; `growth.js` adds the training layer; the Puzzles view is `puzzles-core.js` (pure logic) + `puzzles.js` (view) + lazily loaded `puzzle-data.js` (Lichess CC0 puzzles, regenerate with `scripts/build-puzzle-data.py`, never hand-edit)
- Desktop-first UI: three-column rails, board sized from viewport height (`--board-size`), top nav Library / Coach / Puzzles, Coach right rail tabbed (Game / Practice / Progress), Coach left rail groups collapsible. Below 1024px a desktop notice overlays the page; there is no mobile layout by design
- Client-side only — cm-chessboard, chess.js, jQuery, Supabase JS, and Stockfish are vendored locally
- One board component: `src/ui/board.js` gives every board (`myBoard`, `coachBoard`, `puzzleBoard`, `archiveBoard`) a chessboard.js-style API (`Chessboard(id, config)`, `position`, `orientation`, `flip`, `resize`, `destroy`, `onDragStart`/`onDrop`/`onSnapEnd`, plus `setMarks` for square marks and `moveTargets` for legal-move dots) on top of cm-chessboard 8.15.4 (`vendor/cm-chessboard/`, ES modules loaded by the module script `src/ui/board-module.js`, which runs before DOMContentLoaded). Drag and click/tap share one input path; never add a second click handler on a board. Pieces come from `vendor/pieces/cburnett/sprite.svg`, generated by `scripts/build-piece-sprite.js` (validate-design-tokens.js fails if it is stale). jQuery stays for app code only
- Design system: colours, type, space and board themes are tokens in `styles/tokens.css` (spec: `docs/design-spec.md`, gallery: `docs/design-system/`). `styles.css` uses tokens only, which `scripts/validate-design-tokens.js` enforces; `scripts/check-contrast.js` checks WCAG contrast for both themes. Light/dark follows the device unless Settings overrides it (`ui:theme`, applied before paint by `theme-init.js`). Fonts are self-hosted woff2 in `fonts/` (OFL) because the CSP blocks font CDNs
- Core app logic is split into classic scripts under `src/` (`core/` engine, opponent, classification, tactics, opening book, Library SR, board positions as words for screen readers; `data/` persistence, lifetime stats, account and practice sync; `coach/` insights, practice, daily plan, dashboard, candidates, summary; `ui/`, `library/`), loaded before `app.js` in `index.html`. Their top-level declarations are shared globals, exactly as when they lived in `app.js`. Node validators read the app through `scripts/lib/app-source.js` (load order from `index.html`); `scripts/validate-core.js` loads each `src/core/` file whole and unit-tests it
- Feature modules added on top of `app.js` (each loads after it, keeps its own state, and talks to app globals only through small hooks): `board-overlay.js` (SVG arrows/badges/eval bar over any board, reading square geometry from the rendered `.square[data-square]` rects), `coach-overlay.js`, `move-flair.js` (Great/Brilliant), `explore-analysis.js` (engine lines in Explore; never `engineClient.cancel()` from here, send UCI `stop`), `game-archive.js`, `game-import.js` + `game-import-core.js` (import games by username from the public Chess.com/Lichess APIs, reviewed into the archive and Insights), `opponents.js` (bot personas; book moves only, the calibrated selector is untouched), `activity.js`, `shortcuts.js`, `endgames.js`, `repertoire-core.js` (spaced-repetition repertoire drills, played by puzzles.js), `clock-core.js` + `coach-clock.js` (optional Coach time controls; flags end the game through `coachFinishGame`). Pure logic in these files has a Node validator (`validate-puzzles`, `-move-flair`, `-opponents`, `-activity`, `-endgames`, `-game-import`, `-repertoire`, `-clock`); UI is covered by `verify-puzzle-journeys.js` and `verify-behaviour-units.js`
- Lichess Opening Explorer API for Explore mode (user supplies their own Lichess Personal Access Token, kept in sessionStorage only)
- Optional Supabase account sync; Coach remains fully usable in local-only mode
- Browser-only by design: no web app manifest, no service worker registration, no install prompt. Installed copies captured magic-link URLs and opened them outside the browser. `service-worker.js` stays as a kill switch for earlier installs.
- The Supabase project serves chess only. OOTD (ootd.cjarhodes.com) shared it briefly in November 2026 and has moved to its own sign-in and storage. Its empty `ootd_` tables, `ootd_save_wardrobe` function and `ootd-photos` bucket (from `20261105222014_ootd_accounts.sql`, kept for migration history) are left over and can be dropped with a follow-up migration. The Magic Link email template no longer needs to stay neutral.
- Sign-in is a Supabase magic link, plus an emailed 6-digit code (`verifyOtp`) when `emailCodeEnabled` is true in `coach-config.js`. The flag stays off until the project's Magic Link email template carries `{{ .Token }}`, which needs custom SMTP, a Pro plan, or a Send Email hook. The template lives in `supabase/templates/magic_link.html`.

## Local preview
Serve the folder over HTTP so workers and browser security rules behave like production:

```sh
python3 -m http.server 4173 --bind 127.0.0.1
```

Then open `http://127.0.0.1:4173/`.

## Workflow
1. Edit `index.html`, `app.js`, the relevant `src/` or feature-module file, or the vendored/config file. A new `src/` file needs a `<script>` tag before `app.js` in `index.html`.
2. Run `node --check` on `app.js` and the feature modules, and every `scripts/validate-*.js` validator (`validate-core.js` also parses every `src/` file).
3. Run `scripts/verify-browser.sh` for the repeatable Library, Coach, practice-loop, journey and behaviour-unit coverage. Test behaviour, not source text: new checks go in `scripts/verify-behaviour-units.js` (browser, stub only the boundary) or a Node validator that runs the logic, never a regex over `app.js`. Checks on shipped files (migrations, CI, CSP) belong in `validate-schema.js` / `validate-security.js`.
4. For schema changes, add a Supabase migration and run a local reset or linked `supabase db push`.
5. If you add or change a line in `openings.js`, run `node scripts/audit-openings.js <ids>` (engine check: the owning side's moves must not give away more than 10 points of winning chances; trap victims' moves are reported, not failed). Line ownership for traps and gambits lives in `LINE_SIDE` in `opponents.js` and is read through `openingLineSide` in `app.js`.
6. If you touch `COACH_DIFFICULTY_KEYFRAMES` or `chooseCalibratedOpponentMove` (both in `src/core/opponent.js`), run `node scripts/calibrate-difficulty.js` (several minutes; uses the vendored engine). Check the difficulty trend, severe-blunder and mate-in-one rates as well as ACPL. The seeded suite measures regression proxies, not human Elo; do not tune toward an unsourced human ACPL curve.
7. Commit and push to `main`; Vercel auto-deploys to chess.cjarhodes.com.
8. Confirm the deployment and smoke-test the custom domain.
