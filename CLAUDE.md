# chess-cjarhodes

Static single-page chess training app served at https://chess.cjarhodes.com.

## Stack
- Static `index.html` + `styles.css` + classic scripts under `src/` (no build step or package manager; `app.js` is now only the small startup file that binds events and boots the app, loaded after `src/views/`); opening content data (move lists, explanations, key ideas, variations) lives in `openings.js`, loaded before `src/`; `growth.js` adds the training layer; the Puzzles view is `puzzles-core.js` (pure logic) + `puzzles.js` (view) + lazily loaded `puzzle-data.js` (Lichess CC0 puzzles, regenerate with `scripts/build-puzzle-data.py`, never hand-edit)
- Settings is one sheet (`src/ui/settings.js`, `#settings-sheet`, a native modal `<dialog>`): the app-bar gear, the `,` shortcut, `[data-settings-open="<section>"]` controls (the Coach rail's Settings link) or `&settings=<section>` open it at Appearance (`ui:theme`, board colours, sounds, `ui:board-feedback`), Account (`#coach-auth-card`) or Training data (`#training-data-card`). Those controls were moved there from Coach's rail with their ids, so `src/views/`, growth.js, coach-overlay.js, account-continuity.js and backup-nudge.js bind them as before; open it in tests through the gear and `#settings-tab-<section>`, not by opening a rail group. Centred card from 760px, bottom sheet in the stacked layout
- Navigation goes through the router (`src/ui/router.js`, loaded before the views): `updateURL()` in `src/views/shell.js` describes the current place as a route and `Router.commit` writes it, pushing a history entry for a new view, opening, line, Library mode, Puzzles mode or for opening Settings, and rewriting the entry otherwise (study moves, Settings sections, closing Settings). Back/Forward run `restoreRoute` (`src/views/shell.js`), which changes only what differs. `parseRoute` keeps the old `?view=`, `?opening=`, `mode=` links as entry points. Nothing is pushed while the page applies the URL it loaded with, nor while a magic-link fragment is waiting to be read (`readCoachAuthUrlState`). Pure route rules are tested by `scripts/validate-router.js`
- Responsive UI with breakpoints at 760px and 1200px (the "RESPONSIVE LAYOUT" section at the end of `styles.css`). From 1200px: three-column rails, board sized from viewport height (`--board-size`, fitted by `fitCoachBoard`/`fitLibraryBoard`), top nav Library / Coach / Puzzles, Coach right rail tabbed (Game / Practice / Progress), Coach left rail groups collapsible. 760–1199px landscape: the same three columns with narrower rails. Stacked (below 760px, below 1200px held upright, or a sideways phone): one column with the board edge to edge (sized from the width in CSS), the notation as a scrolling strip under the board, the panels below, and the top nav as a bottom tab bar. `src/ui/layout.js` holds `LAYOUT_STACKED_QUERY` (keep it equal to the CSS query), moves the notation into the strip and scrolls back to the board after actions; layout checks run at 375, 820 and 1024px in `verify-behaviour-units.js`. Below 760px a notice (`#desktop-notice`, dismissed per session) first says the phone layout is a preview: magic-link sign-in can open in another browser, and Safari can clear device-only progress after a week without a visit (it points to Settings → Training data for backups). Keep it until both are resolved; between 760 and 1199px there is no notice
- Client-side only — cm-chessboard, chess.js, Supabase JS, and Stockfish are vendored locally
- One board component: `src/ui/board.js` gives every board (`myBoard`, `coachBoard`, `puzzleBoard`, `archiveBoard`) a chessboard.js-style API (`Chessboard(id, config)`, `position`, `orientation`, `flip`, `resize`, `destroy`, `onDragStart`/`onDrop`/`onSnapEnd`, plus `setMarks` for square marks and `moveTargets` for legal-move dots) on top of cm-chessboard 8.15.4 (`vendor/cm-chessboard/`, ES modules loaded by the module script `src/ui/board-module.js`, which runs before DOMContentLoaded). Drag and click/tap share one input path; never add a second click handler on a board. Pieces come from `vendor/pieces/cburnett/sprite.svg`, generated by `scripts/build-piece-sprite.js` (validate-design-tokens.js fails if it is stale).
- No jQuery: app code uses plain DOM APIs plus the small helpers in `src/ui/dom.js`, loaded first (`byId`, `qs`, `qsa`; `on(target, type, [selector,] handler)` for binding and delegation, `this` being the bound or matched element; `onReady`, which runs startup handlers in order after every DOMContentLoaded listener; `showEl` / `hideEl` / `toggleEl`, which keep jQuery's display rules: hiding remembers an inline display such as `flex`, and showing an element its stylesheet hides gives it its tag's default display; `isVisible`; `makeEl`). Keep it a handful of helpers; Node validators stub them with `scripts/lib/dom-stub.js`
- Design system: colours, type, space and board themes are tokens in `styles/tokens.css` (spec: `docs/design-spec.md`, gallery: `docs/design-system/`). `styles.css` uses tokens only, which `scripts/validate-design-tokens.js` enforces; `scripts/check-contrast.js` checks WCAG contrast for both themes. Light/dark follows the device unless Settings → Appearance overrides it (`ui:theme`, applied before paint by `theme-init.js`). Fonts are self-hosted woff2 in `fonts/` (OFL) because the CSP blocks font CDNs
- Core app logic is split into classic scripts under `src/` (`core/` engine, opponent, classification, tactics, opening book, Library SR, board positions as words for screen readers; `data/` persistence, lifetime stats, account and practice sync; `coach/` insights, practice, daily plan, dashboard, candidates, summary; `ui/`, `library/`; then `views/`, which holds what was in `app.js` until Phase 6: `shell.js` (current view and view switching, the route, account and device-scoped storage state, board last-move marks, themes, phone notice, board fitting, promotion picker, keyboard move parsing), `library.js` (Library view: Study / Quiz / Explore), `coach.js` (Coach game loop, board, controls, panel tabs, summary overlay), `coach-review.js` (review card, analysis line, review cursor, captured pieces, move list / PGN), `coach-practice.js` (mistake drills)), in that order in `index.html`, followed by `app.js` (the ready handler, run by `onReady`: event binding and startup). Their top-level declarations are shared globals (classic scripts share one global scope; only plain initialisers and the ready handler run at load, so the files can call each other freely). Node validators read the app through `scripts/lib/app-source.js` (load order from `index.html`); `scripts/validate-core.js` loads each `src/core/` file whole and unit-tests it
- Feature modules added on top of the views (each loads after `app.js`, keeps its own state, and talks to app globals only through small hooks): `board-overlay.js` (SVG arrows/badges/eval bar over any board, reading square geometry from the rendered `.square[data-square]` rects), `coach-overlay.js`, `move-flair.js` (Great/Brilliant), `explore-analysis.js` (engine lines in Explore; never `engineClient.cancel()` from here, send UCI `stop`), `game-archive.js`, `game-import.js` + `game-import-core.js` (import games by username from the public Chess.com/Lichess APIs, reviewed into the archive and Insights), `opponents.js` (bot personas; book moves only, the calibrated selector is untouched), `activity.js`, `shortcuts.js`, `endgames.js`, `repertoire-core.js` (spaced-repetition repertoire drills, played by puzzles.js), `clock-core.js` + `coach-clock.js` (optional Coach time controls; flags end the game through `coachFinishGame`), `backup-nudge.js` ("Last backed up" in Settings → Training data, and the phone-only reminder for signed-out users with progress, whose Sign in to sync opens Settings → Account; it is decided at load, after the account check, never mid-game; `exportTrainingBackupNow` in growth.js records the time). Pure logic in these files has a Node validator (`validate-puzzles`, `-move-flair`, `-opponents`, `-activity`, `-endgames`, `-game-import`, `-repertoire`, `-clock`, `-backup-nudge`); UI is covered by `verify-puzzle-journeys.js` and `verify-behaviour-units.js`
- Lichess Opening Explorer API for Explore mode (user supplies their own Lichess Personal Access Token, kept in sessionStorage only)
- Optional Supabase account sync; Coach remains fully usable in local-only mode
- Browser-only by design: no web app manifest, no service worker registration, no install prompt. Installed copies captured magic-link URLs and opened them outside the browser. `service-worker.js` stays as a kill switch for earlier installs.
- The Supabase project serves chess only. OOTD (ootd.cjarhodes.com) shared it briefly in November 2026 and has moved to its own sign-in and storage. Its `ootd_` tables, `ootd_save_wardrobe` function and `ootd-photos` bucket (created by `20261105222014_ootd_accounts.sql`, kept for migration history) are dropped by `20261108060000_drop_ootd_objects.sql`, which stops rather than delete anything with data behind it (bucket files must be removed through the Storage API first); `supabase/tests/database/ootd_objects_dropped.test.sql` checks they are gone. The Magic Link email template no longer needs to stay neutral.
- Sign-in is a Supabase magic link, plus an emailed 6-digit code (`verifyOtp`) when `emailCodeEnabled` is true in `coach-config.js`. The flag stays off until the project's Magic Link email template carries `{{ .Token }}`, which needs custom SMTP, a Pro plan, or a Send Email hook. The template lives in `supabase/templates/magic_link.html`.

## Local preview
Serve the folder over HTTP so workers and browser security rules behave like production:

```sh
python3 -m http.server 4173 --bind 127.0.0.1
```

Then open `http://127.0.0.1:4173/`.

## Workflow
1. Edit `index.html`, the relevant `src/` (views in `src/views/`) or feature-module file, or the vendored/config file. A new `src/` file needs a `<script>` tag in `index.html` before `app.js` (and before `growth.js`), which `scripts/lib/app-source.js` then picks up.
2. Run `node --check` on `src/*/*.js` and the feature modules, and every `scripts/validate-*.js` validator (`validate-core.js` also parses every `src/` file).
3. Run `scripts/verify-browser.sh` for the repeatable Library, Coach, practice-loop, journey and behaviour-unit coverage. Test behaviour, not source text: new checks go in `scripts/verify-behaviour-units.js` (browser, stub only the boundary) or a Node validator that runs the logic, never a regex over the app source. Checks on shipped files (migrations, CI, CSP) belong in `validate-schema.js` / `validate-security.js`.
4. For schema changes, add a Supabase migration and run a local reset or linked `supabase db push`.
5. If you add or change a line in `openings.js`, run `node scripts/audit-openings.js <ids>` (engine check: the owning side's moves must not give away more than 10 points of winning chances; trap victims' moves are reported, not failed). Line ownership for traps and gambits lives in `LINE_SIDE` in `opponents.js` and is read through `openingLineSide` in `src/views/library.js`.
6. If you touch `COACH_DIFFICULTY_KEYFRAMES` or `chooseCalibratedOpponentMove` (both in `src/core/opponent.js`), run `node scripts/calibrate-difficulty.js` (several minutes; uses the vendored engine). Check the difficulty trend, severe-blunder and mate-in-one rates as well as ACPL. The seeded suite measures regression proxies, not human Elo; do not tune toward an unsourced human ACPL curve.
7. Commit and push to `main`; Vercel auto-deploys to chess.cjarhodes.com.
8. Confirm the deployment and smoke-test the custom domain.
